# Codex 计划模式与常用 AGENT 规则

> 分享时长：约 20 分钟  
> 适合听众：已经使用过 AI 编程工具的开发者

## 一、为什么需要 AGENT 规则（约 2 分钟）

同一个需求交给 AI，有时写得不错，有时却不符合项目习惯。AI 会写代码，但它一开始并不知道我们的技术选型和团队要求。例如：接口字段必须使用下划线，修改代码后必须运行指定检查。

每次对话都重新说明，既麻烦又容易遗漏。

`AGENTS.md` 就是“给 AI 看的项目说明书”。把长期有效的要求写进去，Codex 进入项目后会按照这些规则工作。

> 演讲提示：这里可以问大家，“你有没有反复提醒 AI 同一件事？”

## 二、常用的 AGENT 规则（约 8 分钟）

一份实用的 `AGENTS.md`，写清楚下面五类内容就够了。

### 1. 项目介绍

告诉 Codex 项目用途、所用技术和主要目录，避免它找错入口。

### 2. 常用命令

写清楚如何安装依赖、启动项目、构建和检查。例如 `npm run build`、`npm run check`。命令比“修改后记得测试”更明确。

### 3. 代码规范

保留团队真正关心的要求，例如命名、注释、禁止魔法值和避免重复代码。格式化工具能自动处理的内容不必反复强调。

### 4. 安全边界

明确不能提交密码和 Token、不能随便修改生产环境，也不能破坏用户已有改动。

### 5. 交付要求

要求 Codex 运行检查，并说明改了什么、验证了什么、还有什么没有验证。

下面是一份可以直接修改的精简模板：

```markdown
# AGENTS.md

## 项目说明

这是一个使用 Node.js 和 MySQL 的内容管理系统。
主要代码在 `src/`，数据库脚本在 `database/`。

## 常用命令

- 安装依赖：`npm ci`
- 本地启动：`npm run dev`
- 完整检查：`npm run check`

## 代码要求

- 方法和变量使用 lowerCamelCase。
- 对外 API 字段使用 snake_case。
- 禁止在代码中写入密码、Token 和私钥。
- 不要修改 `dist/` 等自动生成的文件。

## 完成交付

- 修改后运行与改动范围对应的检查。
- 说明修改内容、检查结果和未验证事项。
- 保留工作区中与当前任务无关的改动。
```

编写规则时记住三点：第一，要具体，不要只写“保证代码质量”；第二，尽量给出命令、路径或例子；第三，只留下重要规则，文档太长反而容易让重点消失。

> 演讲提示：展示模板时，可以让大家想一条自己团队每天都会重复提醒的规则。

## 三、什么是计划模式（约 3 分钟）

计划模式可以用一句话说明：

> 计划模式就是让 Codex 先调查、再提问、最后给方案，暂时不修改代码。

如果需求很小而且非常清楚，例如“把按钮文字改成提交”，可以直接执行。

需求涉及多个模块，或者关键问题还没确定时，先使用计划模式更合适。重点不是把计划写长，而是在编码前发现问题、减少返工。

## 四、计划模式怎么工作（约 5 分钟）

计划模式通常分为三个步骤：

1. Codex 先查看代码、配置和现有实现，了解项目真实情况。
2. 对代码中无法确定、但会影响方案的问题向用户提问。
3. 输出实施计划，写清楚改什么、怎么改、如何验证。

例如，我们只说一句：“给博客增加文章收藏功能。”

Codex 不应该马上创建数据库表。它会先检查登录、文章存储和前端请求方式，再确认：收藏是否必须登录？能否取消？是否展示数量？

确认后，Codex 再给出数据库、API、页面和测试方案，并检查登录和越权问题。

用户确认计划后，再进入执行阶段。这样开发人员审核的是方案，Codex 执行的是已经确定的方案。

> 演讲提示：重点不是问题越多越好，而是只问那些会改变实现方案的问题。

## 五、两者如何配合（约 1 分钟）

整个过程可以概括成一条线：

`AGENTS.md 提供长期规则 → 计划模式确定本次方案 → 确认后执行和验证`

`AGENTS.md` 管长期习惯，计划模式管当前任务。项目规则越清楚，计划阶段需要反复确认的事情就越少。

## 六、总结（约 1 分钟）

最后记住三句话：

1. 把经常重复的项目要求写进 `AGENTS.md`。
2. 复杂或不确定的任务，先使用计划模式。
3. 好计划不在于长，而在于写清楚改什么、怎么验证。
